## Docker Compose stack

The `.devcontainer/compose.yaml` file defines a single `workspace` service built from `.devcontainer/Dockerfile`. Compose assigns the workspace container's name automatically.

### Workspace and services

The native `mounts` setting in `.devcontainer/devcontainer.json` bind-mounts `${localWorkspaceFolder}` at `/workspace/${localWorkspaceFolderBasename}`, using the local repository folder name. The matching `workspaceFolder` opens VS Code there; terminals and lifecycle commands use this directory. Dev Container Features, VS Code settings, lifecycle commands, and named volumes remain configured in `devcontainer.json`.

The Docker image's default working directory is `/workspace`. Rebuild the devcontainer to apply a path change. VS Code connects to the `workspace` Compose service as `vscode`. The service runs `sleep infinity` to stay available. Closing the devcontainer's VS Code window stops the Compose stack through `shutdownAction: stopCompose`.

To expand the stack, add services alongside `workspace` in `compose.yaml`. Dev Containers starts all services by default. Services communicate using Compose service names, such as `db` or `redis`, as hostnames. No database or additional application service is configured in this template.

## Persistent agent data

`<folder>` below is the local repository folder name.

| Named volume | Container path | Contents |
| --- | --- | --- |
| `<folder>-codex` | `/home/vscode/.codex` | Codex data and authentication |
| `<folder>-agent-skills` | `/home/vscode/.agents` | Canonical agent-skill store |
| `<folder>-treehouse` | `/home/vscode/.treehouse` | Treehouse worktree pool |

These named volumes survive devcontainer rebuilds. They are separate from the repository bind mount.

## Persistent Docker-in-Docker data

The [Docker-in-Docker Feature](https://github.com/devcontainers/features/blob/main/src/docker-in-docker/devcontainer-feature.json) automatically adds these named volumes. `${devcontainerId}` is the identifier generated by Dev Containers.

| Named volume | Container path | Contents |
| --- | --- | --- |
| `dind-var-lib-docker-${devcontainerId}` | `/var/lib/docker` | Docker daemon state, named volumes, and build cache |
| `dind-var-lib-containerd-${devcontainerId}` | `/var/lib/containerd` | Container image content and snapshots |

These volumes preserve the inner Docker environment's data across rebuilds with the same devcontainer ID.

## Devcontainer creation lifecycle

These steps describe how the development environment is initialized, built, and configured when you create or rebuild the devcontainer.

1. **Before creation:** the inline `initializeCommand` derives the repository prefix and writes Git identity and the GitHub token to `.devcontainer/.env.workspace` on the host. The generated file is Git-ignored and excluded from the Docker build context. Mount paths use native Dev Container variable substitution without an initialization script or generated path settings.
2. **During build:** the Dockerfile installs its toolchain; Dev Container Features add Node.js and Docker-in-Docker.
3. **After creation:** `postCreateCommand` fixes ownership of the persistent directories, adds the workspace as a Git safe directory, installs the pinned Matt Pocock skills and the repository's `setup-workspace` skill globally for Codex, and runs `npm --prefix website ci`. The local setup skill is refreshed from the repository on rebuild; start its guided workflow from an agent session as described in [Post-stack creation configuration](getting-started/post-creation.md).

Port **3000** is forwarded as **Documentation**. The docs server is started on demand.
